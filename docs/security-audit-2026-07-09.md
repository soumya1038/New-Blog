# Security Audit - 2026-07-09

Scope: repository-wide first pass across backend, frontend, service code, deployment files, dependency manifests, local ignored env files, and high-risk user-data paths.

## Fixed in this pass

- Profile responses no longer expose raw API keys or internal auth/security fields. Other-user profiles now use a public allowlist with privacy-aware email, phone, social link, and status handling.
- API-key listing now returns masked previews only. Newly generated keys are still returned once by the create response so the user can copy them.
- Newly generated app API keys now use a project-owned `lk_live_` prefix instead of an OpenAI-like `sk-proj-` prefix, reducing scanner confusion while preserving existing key compatibility.
- Razorpay payment verification now binds the signature to the authenticated buyer, stored Razorpay order id, pending order status, captured payment amount, and currency. Invalid signatures no longer mark arbitrary orders as failed.
- Marketplace checkout now rejects invalid product ids, unsupported or mixed currencies, and non-integer/out-of-range physical quantities before stock reservation. This closes a stock/pricing bug where negative quantities could increase inventory or distort totals.
- Digital-product download URLs now require valid ids and reserve a download count with an atomic order update before issuing the signed Cloudinary URL, closing the concurrent-download limit bypass window.
- Seller order APIs now return seller-scoped order views: only the seller's own items, no buyer email, no payment identifiers, and shipping details only when the seller owns a physical item that needs fulfillment.
- Seller order-wide ship/deliver actions now reject multi-seller orders and incompatible mixed fulfillment types until item-level fulfillment exists, preventing one seller from changing another seller's order state.
- Seller order routes now register seller/admin namespaces before buyer `/:id` routes, so seller order-list and fulfillment endpoints are not shadowed by order-id handlers.
- Order list endpoints now cap pagination limits, restock requests require strict integer quantities with a configurable maximum, and invalid order/product/user ids return 400 instead of bubbling cast errors.
- Seller-created coupons are now forced to seller scope, can only target the seller's own products, and validate discount amounts, usage limits, applicable types, dates, and product ids before creation.
- Seller earnings/admin payout list endpoints now cap pagination. Seller earnings summaries are computed with Mongo aggregation instead of loading every earning document into memory.
- Payout requests now atomically claim available earnings with a status filter before processing, and conflicting concurrent payout attempts fail with 409 instead of creating a duplicate claim.
- Price-change request endpoints now validate request ids, bound list limits, trim admin notes, and avoid returning seller email in seller-owned request responses.
- Cart add/update now uses the same strict quantity model as checkout: whole-number caps, active-product validation, stock/minimum checks for physical products, and single-quantity digital/service items. Wishlist/cart removal routes now reject invalid product ids cleanly.
- Seller onboarding no longer trusts a client-supplied `verificationProvider: "razorpay"` flag as proof of verification. Until a backend Razorpay verification callback/record exists, applications remain manual-review/pending-provider instead of being marked verified.
- Seller store settings now validate featured product ids, require featured products to belong to the seller's active listings, bound editable text/social fields, and omit internal `bannerPublicId`/ownership metadata from public store responses.
- Admin seller-application listing now caps pagination, review actions validate application ids, review notes are bounded, and seller-application socket notifications no longer require Socket.IO to be present.
- LiveKit group-call routes now require group membership before issuing tokens, starting calls, ending calls, or reading active/history state.
- Socket.IO now requires JWT authentication during the handshake and derives `socket.userId` from the token instead of trusting browser-supplied user ids.
- Socket message read/reaction and group-call events now perform participant or group membership checks.
- Direct-call logs now validate receiver ids, block relationships, self-calls, call types, call statuses, durations, and timestamps. New call logs start as missed until a later participant update marks the final outcome.
- Direct-call signaling over Socket.IO now requires a verified call-log-backed session before relaying incoming calls, offers, answers, ICE candidates, rejects, or ended events between users.
- Call-log deletion is now per-user via `deletedBy`; one participant no longer deletes the other participant's history entry unless both participants delete it.
- Product descriptions no longer render seller-controlled HTML with `dangerouslySetInnerHTML`; they render as plain text.
- Chat user search and blocked/muted user payloads no longer return email addresses.
- Call log updates now require the authenticated user to be a call participant.
- Chat file uploads now require a valid receiver, enforce block/self checks, and require both extension and MIME type to match the allowed list.
- Chat file uploads now use disk-backed temp files streamed to Cloudinary instead of buffering up to 50MB in Node memory. `CHAT_FILE_UPLOAD_MAX_MB` and `CHAT_FILE_UPLOAD_TEMP_DIR` are configurable.
- Public `/health` no longer returns internal metrics; detailed metrics remain behind admin routes.
- API keys are now stored as keyed hashes for new keys, masked in API/profile responses, and supported by a migration script for legacy plaintext keys. Legacy keys are upgraded on successful use.
- `backend/utils/encryption.js` no longer has a hardcoded encryption secret fallback; startup diagnostics require `ENCRYPTION_KEY` and check minimum secret length.
- WebRTC TURN credentials are no longer built into the frontend. Authenticated clients now fetch ICE servers from the backend, which can mint short-lived TURN REST credentials from `TURN_STATIC_AUTH_SECRET`.
- Production dependency audits are clean after backend package updates/overrides and removing unused frontend `fabric`.
- Registration, password reset, forgot-password, authenticated password change, profile password change, and account deletion email codes now use Mongo TTL records with HMAC-hashed codes, attempt limits, and crypto-random generation instead of process-local `global.*` maps.
- Pending password-change flows now store a bcrypt password hash in short-lived metadata instead of storing the future password in plaintext.
- Group invite codes now use crypto-random tokens.
- Two-factor challenge signing no longer falls back to weak hardcoded or unrelated service secrets.
- Email/SMS transport logging no longer prints recipient addresses, phone numbers, subjects, or Brevo response bodies. The unused `mailService.backup.js`, `sendEmail.js`, `testRegister.js`, and `fixEmailIndex.js` artifacts were removed.
- Contact/admin email delivery no longer has a hardcoded personal fallback address; `SUPPORT_ADMIN_EMAIL`/`MY_EMAIL` must be configured.
- Seller upload routes now authenticate before parsing upload bodies, preventing unauthenticated clients from forcing memory/disk upload work.
- Digital product file uploads now use disk-backed temp files streamed to Cloudinary instead of buffering up to 500MB in Node memory. Allowed extensions and max size are configurable.
- Digital product temp uploads now default to `backend/tmp/digital-temp` instead of the publicly served `/uploads` tree, with `DIGITAL_UPLOAD_TEMP_DIR` available for private deployment-specific temp storage.
- Helmet CSP is enabled with explicit directives for known app sources, plus environment extension points for future trusted sources.
- OAuth state replay markers and Facebook data-deletion status now use a Mongo TTL-backed temporary state store instead of process-local maps.
- HTTP rate limiters can use Redis-backed shared counters when `RATE_LIMIT_REDIS_URL` or `REDIS_URL` is configured, with in-memory fallback for local/dev.
- High-volume Socket.IO events now have per-socket throttles for chat messages, reactions, typing, call offers/answers, and ICE candidates.
- Root Dockerfile and docker-compose now match the actual `backend`/`redirect` layout. The production image builds the React app, serves it from the backend, runs as a non-root user, and excludes local env/build/upload artifacts through `.dockerignore`.
- Docker Compose no longer references nonexistent `apps/*`, no longer publishes MongoDB/Redis ports by default, and no longer commits hardcoded database credentials.
- Root workspace metadata and lockfile now reference `backend` and `redirect` instead of stale `apps/*` workspaces, and the unused root `docker` npm package was removed.
- Frontend NewsData/OpenWeather fallback API keys were removed from committed client code. News, cricket, and weather widgets now fail closed with unavailable states when public widget keys are not configured, and `redirect/.env.example` documents the optional keys.
- Stale standalone credential/database test scripts were removed from tracked backend source: `testAI.js`, `testGroq.js`, `testCloudinary.js`, `testDrafts.js`, `test-livekit.js`, and `test-groups.js`.
- `fix-slug-index.js` no longer falls back to a local MongoDB URI and no longer logs full Mongo connection error objects.
- Socket debug logging no longer prints user ids, receiver ids, member ids, socket ids, online-user lists, route-change/disconnect activity, message ids, or call-room state. Email/auth logging now records error messages instead of full exception objects in high-risk flows.
- Blog creation/listing, message cleanup, admin suspend, and chat voice/audio debug logs no longer dump user content, backend response payloads, message ids, or call metadata into server/browser consoles.
- `/api/ai/summarize` now requires authentication like the other AI generation endpoints.
- `/api/admin/health` now requires admin/co-admin authentication. Public uptime checks remain available at `/health` and `/ready` with limited output.
- `/api/system/bg-remover/warmup` now requires admin/co-admin authentication, and the frontend background-removal warmup hook is disabled by default unless `REACT_APP_ENABLE_BG_REMOVER_WARMUP=true`.
- `/api/test` is now development-only instead of being exposed in production.
- Message Cloudinary cleanup now uses the existing `utils/cloudinary` module instead of a nonexistent `config/cloudinary` path, and cleanup logs no longer print storage public IDs.
- Blog/editor image uploads now use user-scoped Cloudinary folders, and `DELETE /api/blogs/delete-image` only deletes ids in the caller's scoped upload folder or ids referenced by Blog/Article/Short records owned by that caller. Frontend delete calls now use query params so foldered public ids are handled correctly.
- Blog, article, and short create/update handlers now reject new cover/gallery Cloudinary public ids unless they are in the caller's scoped upload folder or are unchanged legacy ids already on that caller's own document. This prevents saved content records from becoming cleanup handles for another user's Cloudinary assets.
- Public guest analytics tracking now validates anonymous session ids, bounds stored path/user-agent values, caps page duration increments, and keeps only the latest configured page entries per session to avoid unbounded document growth.
- External API blog reads now cap pagination, return lean public projections, validate ObjectIds, and require `isDraft: false` for unauthenticated single-blog reads so draft posts cannot be fetched by id through `/api/external/blogs/:id`.
- Public blog, article, legacy short-blog, and short feeds now enforce bounded result sizes by default. Blog/article cache keys now ignore unsupported query parameters, short feeds use bounded page/limit metadata with configurable caps, and malformed author filters now return 400 before cache/database work.
- Public comment and reply reads now enforce default result bounds, normalize cache keys to supported pagination/content flags, and reject malformed short/comment ids before cache/database work. Blog/article detail screens now use the server-provided `replyCount` instead of sending one extra replies request per visible comment.
- Admin user, guest, blog, article, and short listing endpoints now paginate with configurable page/limit caps and total metadata instead of loading every row plus per-row counts. Admin stats date ranges are capped, and the dashboard requests the bounded maximum page size.
- Draft listing and stale-draft cleanup now use configurable list and cleanup batch caps. Blog/article/short draft=true cleanup paths share a type-aware helper that deletes only the matching comment/notification relations and includes gallery image cleanup.
- Messaging and notification reads now enforce configurable caps for conversations, direct/group messages, and notification lists. Chat search input is length-capped and regex-escaped, and malformed user/message/group/notification ids now return 400 before database work across messaging/social actions.
- Product review submission now validates product/order/rating inputs before database work and recomputes rating totals with aggregation instead of loading every review for the product.
- Group chat lists now enforce configurable group-list and member-count caps, validate group/member route ids centrally, and request a bounded group list from the chat UI. Group call history now validates ids and enforces configurable history limits.
- Seller coupon listing now uses configurable page/limit caps with total metadata, and the seller dashboard requests the bounded maximum page size.
- Seller payout requests now load and claim only a configurable bounded earning batch, while returning whether more available earnings remain for later payout requests. Seller product lists and template preset lists now enforce configurable limits, and template preset mutations reject malformed ids before Mongo casting.
- Status availability checks now require a bounded array of valid user ids instead of accepting arbitrary fan-out payloads.
- Backend responses with HTTP 500 status are now centrally sanitized unless `EXPOSE_INTERNAL_ERRORS=true` is explicitly set, preventing inline catch blocks from leaking database/provider/path details through `error.message`.
- Frontend auth storage now honors non-remembered sessions by storing those tokens in `sessionStorage` instead of always persisting them in `localStorage`. Token reads are centralized through `authSession` helpers so API calls, sockets, OAuth callbacks, guest tracking, and UI auth checks use the same source.
- Frontend sensitive local persistence was reduced further: legacy saved username/password credentials are purged from the login screen, checkout address books migrate from long-lived `localStorage` to per-session storage, and chatbot history migrates from long-lived `localStorage` to per-session storage while deleting the legacy keys.
- Additional frontend activity/location persistence now uses session-backed storage with localStorage cleanup for delivery pincode, marketplace personalization, status-view state, story-view state, and active call state. Long-lived localStorage is still retained for low-risk preferences and deliberately durable guest/saved-item caches.
- Product listing local working copies in IndexedDB are now scoped by authenticated user id. The old shared `add-product` working-copy record is deleted on authenticated load/save/cancel so one seller cannot restore another seller's unsaved product draft, images, or digital file on a shared browser profile.

Multer upload validation errors now return 400/413 instead of leaking through generic 500 handling.

- Two-factor setup and disablement now require password step-up tokens, then 2FA step-up tokens when the account already has 2FA enabled; the profile UI now gathers both proofs before calling the protected endpoints.

- Account email changes now require password step-up proof, plus 2FA proof when enabled, from both profile-management entry points.

- Admin and co-admin accounts no longer bypass sensitive-action proof. High-risk admin writes now require password step-up proof and 2FA proof when enabled, covering user deletion/suspension/verification/role changes, warning emails, content deletion, seller-application review, payout completion, price-change review, seller revocation, and support-request updates.
- Support request admin responses now use a serializer instead of returning raw Mongoose documents, authenticated user support lists explicitly omit admin event history, admin support queues no longer populate the linked account email, malformed support request ids return 400 before database work, and support-request admin changes append a bounded per-ticket admin history that is visible in the admin support panel without duplicating internal note contents.

### Residual risk register

- High scale architecture: follower/following/block/mute, likes, and some viewer arrays remain embedded in MongoDB documents. They are bounded or narrowly queried in high-risk paths, but very large accounts can approach MongoDB's document limit. Migrate these relationships to indexed edge collections before supporting high-fanout accounts.
- Browser token blast radius: JWTs remain in session storage, with optional local storage for remember-me. XSS defenses are improved, but HttpOnly Secure SameSite cookies plus CSRF protection would further reduce token theft impact.
- At-rest privacy: email, phone, shipping/support details, and some call/payment metadata remain plaintext inside the database. Apply provider/KMS-backed field encryption and a formally approved retention schedule where threat/compliance requirements demand it.
- Cross-provider atomicity: MongoDB, Cloudinary, Razorpay, email, and LiveKit cannot share one transaction. Compensation/retry paths now retain recoverable state, but durable outbox processing is still recommended for guaranteed side effects.
- Small concurrency windows: the five-pin direct-chat cap and pending-payment cap can briefly exceed their display/business caps under simultaneous requests for different records. State remains authorized and bounded by expiry/cleanup, but strict global caps require a per-conversation/per-user counter document or distributed lock.
- Existing legacy public status media remains public until those short-lived statuses expire or are migrated; all new status media uses authenticated delivery.
- Operational validation: real Razorpay capture/refund/webhook replay, Cloudinary private delivery, LiveKit calls, production queue failover, backup/restore, authenticated DAST, and sustained multi-instance load tests were not run with production credentials.
